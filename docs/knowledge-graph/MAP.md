## What this app is (60-second orientation)

GamerHoard is a **local, single-user video-game library**: a web app served by `server/index.mjs` (port 5207), MCP tools for Faustus and an optional native Expo app, all over ONE library file (`~/.gamerhoard/library.json`). No accounts, no cloud. You build a library of games, track their state (**Pendiente · Jugando · Pausado · Completado · Abandonado**), tick off **DLCs/expansions**, log **play sessions**, mark which **platforms** you own each game on, rate them and keep private notes. Metadata comes from **RAWG** (through the local server, which keeps the key); the hero import is your **Steam** library (owned games + playtime).

**Inherited names, new meaning (read this or you WILL be confused):** the client keeps an older tracker's schema names to minimise churn. A **`show` / `tvdb_id` is a GAME** (RAWG id; Steam games use `2_000_000_000 + appid`; manual games `1_000_000_000 + hash`), an **`episode` is a DLC/expansion**, **`network` is the studio/publisher**, and the `movie*` methods are legacy stubs. `src/tmdb.ts` is a shim that re-exports `src/rawg.ts`.

**The one abstraction that matters:** every screen talks to a single `DataSource` interface (`apps/mobile/src/db/types.ts`, 58 methods). Three interchangeable implementations satisfy it — `LocalApiSource` (REST to the local server, web default), `LocalSource` (SQLite, native), `MemorySource` (browser demo). The active one is chosen at load time in `src/db/index.ts` (native) / `index.web.ts` (web). **If you add a data operation, you implement it in all three** (stubs are fine for features that do not apply to games).

## Change recipes — "where do I edit X?"

**Add a new data operation (e.g. a new user action that persists):**
1. Add the method signature to the `DataSource` interface in `src/db/types.ts`.
2. Implement it in **all three** backends: `src/db/localapi.ts` (REST), `src/db/local.ts` (SQLite), `src/db/memory.ts` (browser demo). For the REST one, add the route in `server/app.mjs` and, if it needs new library fields, in `mcp/library.mjs` (the MCP tools share it).
3. Call it from the screen. The coverage table above should show ✅✅✅ after — re-run the generator to confirm.

**Add a new screen:** create `apps/mobile/app/<route>.tsx` (or `app/<group>/[param].tsx` for dynamic). Expo Router picks it up by filename. Add nav from wherever it should be reachable, add its strings to i18n (EN first, `es.ts` is typed against it) and, if it has a list or a form, register it with `useCopilotView` and extend `src/copilotContext.ts` + its test so Faustus sees it.

**Add a language:** create `src/i18n/<code>.ts` typed as the EN dict, register it in `src/i18n/index.ts` (`LANGS`, `resources`, `addResourceBundle`), and it shows up in the language picker.

**Add / change game metadata (RAWG):** work in `src/rawg.ts` (cached, deduped; on web it goes through `/api/rawg`). It keeps the old export names (`showDetails`, `detailsById`, …) so screens keep compiling. If you add a new fetched host, register it in `API_SIGNS` of `generate.mjs`.

**Touch the Steam import:** screen `app/import.tsx`, client `src/steam.ts` (`importSteam`), server route `POST /api/steam/import`, shared logic `mcp/integrations.mjs`. Never put a Steam key in the bundle or the library file. Owned games get `tvdb_id = STEAM_ID_OFFSET + appid`.

**Change what Faustus sees:** `src/copilotContext.ts` (pure builders, tested in `copilotContext.test.mjs`), screens register with `useCopilotView`, `src/copilot.ts` installs `window.hoardCopilot`. Keep `x-family.copilot.context` in `faustus-plugin.json` in sync.

## Gotchas & landmines

- **Inherited names, new semantics.** `show`/`tvdb_id` = **game**, `episode`/`ep_state` = **DLC**, `network` = **studio/publisher**; `movie*` methods are stubs. `src/tmdb.ts` re-exports `src/rawg.ts`. Grep results for "show"/"episode" are almost always about games/DLCs.
- **Three backends, one contract.** Forgetting one of `local`/`localapi`/`memory` is the most common bug. The coverage table catches it.
- **One library file, two processes.** Only `mcp/library.mjs` touches `library.json`; the server and the MCP process re-read it when the file changes. Library states (`playing`, `paused`, `completed`) map to UI states (`watching`, `stopped`, `archived`) in `db/localapiMap.ts`.
- **Steam IDs are offset.** A Steam-imported game's id is `STEAM_ID_OFFSET (2_000_000_000) + appid`; manual games use `1_000_000_000 + hash`. Ids from 1e9 up have no RAWG record, so `rawg.ts` skips the request. Use `isSteamId` / `appidOf` from `src/steam.ts`.
- **Web vs native split:** `src/db/index.ts` (native, SQLite) vs `src/db/index.web.ts` (web) keep `expo-sqlite` out of the web bundle. Never import `./local` from web code.
- **Build needs a real `node_modules`** next to the repo root: a junction to another checkout makes `expo export` write asset paths outside `dist`.
- **Secrets live in `.env` / the server environment (gitignored), never the repo.** `RAWG_API_KEY` for the server, `EXPO_PUBLIC_RAWG_KEY` only for native builds.

### Inherited names, new semantics — the thing that trips everyone up
The client began as an older series tracker and **kept its schema/method names** with game meaning. Internalise this map or every grep result will mislead you:

| Code name | Actually means |
| --- | --- |
| `show` / `ShowRow` / `tvdb_id` | **a game** (id = RAWG id; Steam games `2_000_000_000 + appid`; manual games `1_000_000_000 + hash`) |
| `episode` / `ep_state` / `watched_episodes` | **a DLC / expansion** (same checklist UI) |
| `network` | **studio / publisher** |
| `season` | **DLC group** |

| `movie*` methods | **legacy stubs**; the web data source returns empty lists |

### Runtime modes
- **Web (default)** → `LocalApiSource` (`src/db/localapi.ts`): the browser talks to the local server, which reads and writes the shared library file. `EXPO_PUBLIC_BACKEND=memory` gives a browser-only demo.
- **Native** → `LocalSource` (SQLite on the device, seeded from `assets/seed.json`, created empty from `seed.sample.json` by `scripts/ensure-seed.js`). It does **not** read the computer's library file.
- There is no cloud backend and no login. `app.config.js` carries no keys; the RAWG key comes from the server environment (web) or `EXPO_PUBLIC_RAWG_KEY` (native builds).

### Game states
Library states `backlog | playing | paused | completed | dropped` ↔ UI states `backlog | watching | stopped | archived | dropped` (`db/localapiMap.ts`); `src/categories.ts` maps UI states to the buckets (Pendiente, Jugando, Pausado, Completado, Abandonado). DLC completion drives the progress bar. DLC are stored by title in the library; the optional `number` keeps the RAWG catalogue position so the checklist matches DLC marked through Faustus.

### Steam import — the must-knows
- Screen `app/import.tsx` → `importSteam(profile, key)` in `src/steam.ts` → web: `POST /api/steam/import` (the server calls Steam, no CORS problem); native: direct Steam Web API calls.
- The profile can be a SteamID64, a profile URL or a vanity name. The Web API key is typed by the user, remembered only in AsyncStorage/localStorage and never written to the library file or logs. Needs the profile's "Game details" set to Public.
- **ID offset:** a Steam game's id = `STEAM_ID_OFFSET (2_000_000_000) + appid`. Use `isSteamId` / `appidOf`.
- **State from playtime:** never played → `backlog`; played in the last 90 days → `playing`; older → `paused`.
- Achievements: MCP tools and `GET /api/games/:id/achievements`; no UI.

### RAWG client (`src/rawg.ts`)
Read-only, in-flight deduped, two-tier cache (memory → AsyncStorage/IndexedDB, 24h TTL), 12s timeout. Web calls go to `/api/rawg/*` (server adds the key; allow-listed paths only); native calls `https://api.rawg.io/api` with `EXPO_PUBLIC_RAWG_KEY`. Ids from 1e9 up have no RAWG record and are never requested. Keeps the old TMDB export names on purpose.

### Faustus copilot
`window.hoardCopilot` (`src/copilot.ts`) is installed from the root layout (web only). Pure builders live in `src/copilotContext.ts`; mounted screens register what they show (visible games, unsaved form fields) with `useCopilotView` (`src/copilotRegistry.ts`). `onTurnEnd` and `hoard:copilot-turn-end` call `refreshAllQueries()` (debounced) so lists refresh without remounting forms. The launcher, the relay routes and the injection come from `server/hoard-commons` (vendored family helpers).

### Landmines
- **Three backends, one contract.** Any `DataSource` method must exist in `local.ts`, `localapi.ts` and `memory.ts`. The coverage table in `MAP.md` catches a miss.
- **One library file, two processes.** Only `mcp/library.mjs` touches it; both processes re-read it when mtime/size changes. REST calls are serialised.
- **Web vs native split.** `src/db/index.ts` vs `src/db/index.web.ts` keep `expo-sqlite` out of the web bundle. Never import `./local` from web code.
- **Real `node_modules` for the web build.** A junction to another checkout makes `expo export` write asset paths outside `dist`.
- **Never commit** `.env`, keystores or `assets/seed.json` (personal data).
